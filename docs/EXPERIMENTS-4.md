# 第四轮：对照实验结果与之后的优化

> 记于 2026-10-03。范围：第四轮交接文档（`docs/HANDOFF-4.md`）的起因实验、第四轮改动后的两次复跑、复跑中发现的问题与随后的修复。
> 偏离记录的编号对应 `NOTES.md`（第 100–109 条），实验表格的精简版也在 `NOTES.md`"真实模型实验"一节。
> 日志与评测用例在 `~/pi-flow-runs/`（不进仓库）。

## 1. 实验设置

- **项目**：团队看板服务（Node 24、ES 模块、无第三方依赖、`node:sqlite`、REST API + 原生 JS 单页前端），需求在 `~/pi-flow-runs/kanban-input/requirement.md`；建完后做一次需求变更（`change.md`）。
- **评分**：`node ~/pi-flow-runs/kanban-bench/hidden.mjs <项目目录> [--change]`，基础 40 个隐藏用例、变更 6 个。"非法 JSON 返回 400"超出需求，两边都不计分。
- **pi-flow 一侧**：`node scripts/real-build.ts --keep --no-replan --desc-file … --feature-file …`。脚本代替用户：阶段闸门一律批准；任务阻塞时回答"同意你给出的建议"（同一任务最多 3 次，超过即停止）；"建议修订计划"时发起 `/flow replan`。
- **原生 pi 对照**：`node scripts/baseline-build.ts`，单会话，`openai-codex/gpt-6.1-sol`（high）。

## 2. 结果总览

| 日期 | 做法 | 模型 | 新建耗时 | 隐藏测试（基础） | 需求变更 | token（输入/输出/缓存读） | 花费 |
|---|---|---|---|---|---|---|---|
| 10-03 | 原生 pi，单会话 | 全部 gpt | **17.6 分钟** | 39/40 | 3.9 分钟，6/6 | 82k / 37k / 1.03M | 约 0.5 美元 |
| 10-03 | pi-flow（第 100 条改动前，逐任务审查） | 设计与审查 gpt，实施 glm | 84 分钟后叫停 | —（10/16 个任务） | — | 1738k / 291k / 21.1M | gpt 部分 3.62 美元 |
| 10-03 | pi-flow 第四轮（复跑一） | 设计与审查 gpt，实施 glm | 约 4 小时后停掉 | —（卡在功能阶段收尾） | — | — | — |
| 10-03 | pi-flow 第四轮（复跑二） | 全部 gpt | **253.6 分钟** | **39/40** | 未完成（停在 F1） | 2209k / 425k / 24.4M | 约 11 美元（按 run 记录的单价估算） |

两边隐藏测试唯一失败的都是不计分的"非法 JSON 返回 400"。复跑二的项目自带 346 个测试全部通过。

**结论**：第四轮之后，pi-flow 的质量与原生 pi 持平，"审查来回打回"不再出现；但耗时约是原生的 12 倍，花费约 20 倍。需求写清楚、四五千行以内的项目，单会话强模型明显更合适。pi-flow 的开销主要来自流程本身（函数级契约、契约锁定后的修订、多角色交接），而不是审查。

## 3. 起因：第四轮改动前的问题（第 100 条之后）

同一份需求，pi-flow 84 分钟后仍在实施阶段（10/16），审查打回 11 次：7 次先行验收测试写错，3 次底座没达到 architect 自己定的、超出需求的契约。第 100 条已处理前两点（实施者边写边测、契约申报超出需求的设计）。剩下的主要问题是**每个任务一次审查，强模型每轮都能挑出新问题**，于是有了第四轮。

## 4. 第四轮改动（第 101–105 条）

| 编号 | 改动 | 要点 |
|---|---|---|
| 101 | 契约写到函数级 | 每个模块一个契约文件，对外函数写名字、参数、返回值、可能的错误；REST 照旧；任务 inputs 列出依赖的契约条目 |
| 102 | 逐任务审查可关闭（`review.per_task`，默认关） | 提交后直接进合并队列，rebase 到集成分支最新后跑**全量** typecheck、lint、test；失败带日志退回，实施者接着上次对话修。设计阶段文档、fix 流程照旧逐任务审查 |
| 103 | 阶段末审查一次（`review.stage_end`，默认开） | 实施阶段的任务全部合入后：强模型审查本阶段全部代码 → 按模块并行修复 → 确认一次 → 全量测试；推进记录在 `stage-review-<阶段>.json`，崩溃后从中途继续 |
| 104 | 两个审查工具 | `flow_review_report` 提交带编号的问题清单（文件必须是具体路径、不能是契约或受保护文件、要有角色能写）；`flow_review_confirm` 参数只有 `{id, resolved, note}`，只能回答已有编号，不能提新问题（Pi 自己也按 schema 拒绝多余字段） |
| 105 | 全量测试失败的有限重试 | 从失败日志里找出出错的文件，交给写过它的模块修，最多两轮；仍失败转"需要你处理" |

## 5. 复跑一：实施用 glm（约 4 小时后停掉）

阶段末审查的完整循环第一次在真实模型上走通（基础设施阶段）：审查查出 11 个问题 → 按模块拆成 3 个修复任务并行 → 确认 6 个已解决、5 个未解决（附原因）→ 再修一轮 → 闸门通过。

但整体被 glm 拖住。各运行合计 glm 418 分钟、gpt 67 分钟（任务并行，合计会超过实际经过的时间）。暴露的问题：

| 问题 | 现象 | 处理 |
|---|---|---|
| 实验环境缺 `CHROME_BIN` | 审查要求浏览器检查必须读 `CHROME_BIN`，脚本没设，修复怎么也过不了全量测试；脚本的"同意建议"改变不了环境，空转约 20 分钟 | 停掉脚本，设好变量后用 `--dir` 续跑（实验设置问题） |
| 重启后任务卡在合并队列 | 提交直接进合并队列后，引擎在"提交"与"合并"之间重启，任务一直停在 queued_merge；`/flow next` 不处理 | **第 106 条**：`/flow next` 先推进程序步骤再派发 |
| 原地打转 | glm 把同一条调试命令连续执行了 281 次，空转近 1 小时；每次工具调用都续租约，看守永远不触发 | **第 107 条**：连续 5 次完全相同的调用拦下并提示换思路，10 次结束本次运行（计失败、重新派发，多次失败后升级模型） |
| 后台测试留下孤儿进程 | glm 把死循环的测试放到后台跑、再结束外层管道，真正的 node 进程留下来，最多同时 6 个，各占满一个 CPU 核 | 手动清理。防护（禁止实施角色后台运行命令、运行结束时清理工作目录在 worktree 内的残留进程）**尚未实现**，待用户决定 |
| 问题多、修得慢 | 功能阶段末审查 27 个问题（大多是真缺陷：未导入的变量、未定义的函数、权限检查顺序不符合契约、页面状态泄漏）；一个前端修复任务跑了 48 分钟 | 用户决定停掉这一轮，实施角色全部换成 gpt 重跑 |

## 6. 复跑二：全部 gpt（253.6 分钟）

| 阶段 | 用时（从开始计） | 情况 |
|---|---|---|
| 需求 S0 | 0–6.5 分钟 | PRD 一次审查通过 |
| 规划 S1 | 6.5–42 分钟 | architect 问了 1 个问题（成员移除后指派怎么处理）；写出 11 个模块、共 760 行的函数级契约，提交 14 个任务 |
| 基础设施 S2 | 42–约 70 分钟 | 3 个任务；阶段审查 2 个问题，一轮修好、确认通过 |
| 功能 S3 | 约 70–约 230 分钟 | 7 个实现任务约 101 分钟时全部合入；阶段审查只有 2 个问题（前端跨视图状态不同步），但修复时发现前端契约缺回调，契约已锁定，于是走了 **3 次计划修订**（修订 → architect 改契约 → 前端再实现），约 1.5 小时 |
| 联调 S4 | 至 253.6 分钟 | 2 个联调任务；阶段审查 0 个问题；闸门通过，合入主分支 |
| 需求变更 | +10.7 分钟后停止 | F0 完成；F1 的 architect 三次要求确认契约细节（脚本对同一任务最多代答 3 次），脚本停止 |

按角色统计（所有运行合计 319 分钟、35 次运行）：前端 110.6 分钟、architect 85.1 分钟、后端 69.2 分钟、联调 24.4 分钟、审查 17.0 分钟、数据库 11.8 分钟、基础设施 1.0 分钟。

**时间花在哪**：
1. **规划 42 分钟**：函数级契约写得细，原生 pi 这时已经写完一半代码。
2. **契约锁定后的修订约 1.5 小时**：起因都是前端内部组件之间的回调，被写进了契约并锁定。
3. **多角色交接**：35 次运行，每次都要重新读任务、契约和代码；审查本身只占 17 分钟。

**做到了的**：审查不再来回打回（三个阶段末审查分别 2、2、0 个问题，都一轮修好）；gpt 实施时没有原地打转、没有孤儿进程。

## 7. 复跑之后的优化（第 108、109 条）

| 编号 | 改动 | 针对 |
|---|---|---|
| 108 | **契约只写模块之间的边界**：别的模块要调用的才写；前端只写它调用的后端接口和页面入口，组件之间的装配回调不写；同一模块内部互相调用的部分不拆成对着契约并行的任务。改了技能 `design-contract`、`decompose-dag`、architect 提示与 S1 验收标准（只靠提示，程序不检查契约内容） | 复跑二中前端内部回调引出的 3 次修订 |
| 109 | **修复任务可以补契约，只能新增**：阶段审查的修复任务（review-fix）可以写 `docs/contracts/`（guard 放行，不受角色可写范围限制，不计入 writes，避免修复任务互斥）；提交时改动或删除了已有行的契约文件被拒；确认任务的 handoff 附上补充的契约，由审查者核对是否改变需求 | 契约漏写时不必走"修订 → 改契约 → 再实现"的整套流程 |

### 第二批优化（第 110–117 条，用户同意 8 项一起改）

按"改动小、收益确定的先做，动状态机的后做"排序：

| 顺序 | 编号 | 改动 | 针对 |
|---|---|---|---|
| 1 | 110 | **残留进程防护**：guard 拦下后台运行（单独的 `&`）、`setsid`、`disown`；子进程结束后结束工作目录在该任务 worktree 或临时目录里的进程 | 复跑一的孤儿进程 |
| 2 | 111 | **修复任务接着原作者的对话**：review-fix 任务 fork 写过这些文件最多的同角色任务的最后一次会话（同模型、≤400 KB），不必重读代码 | 修复任务每次从头读代码 |
| 3 | 112 | **architect 少提问**：有合理默认方案时直接采用，S1/F1 写进提案的 `assumptions`、S0/F0 写进文档的"约束与假设"，批准时列给用户；只有无法合理假设、会改变数据模型或多个接口的才停下来问 | 复跑二的需求变更停在 F1 |
| 4 | 113 | **契约按需写细**：只有被别的任务直接调用的函数写到函数级，只通过自己 REST 接口对外的模块只写接口与数据模型 | 规划阶段 42 分钟 |
| 5 | 114 | **任务粒度跟实施模型走**：拆任务时提示列出各实施角色的模型；强模型按模块或按层拆大任务，小项目每个角色一个任务（共四五个），弱模型按切片拆小任务 | 复跑二 14 个任务、35 次运行的交接开销 |
| 6 | 115 | **纯测试阶段默认不做阶段审查**（`review.test_stages`：skip/light/strong），闸门照样跑全量测试 | 联调阶段审查 0 个问题 |
| 7 | 116 | **批量合并**（`limits.merge_batch`，默认 3）：队首连续的普通任务先叠加、只跑一次全量测试，通过后依次快进（仍只有一个 merging）；失败或有不适合的任务时退回逐个合并 | 每次合并都串行跑全量测试 |
| 8 | 117 | **阶段审查按角色分批提前开始**：某角色的任务全部合入就开一批审查，与其他角色的任务并行；每批各自审查 → 修复 → 确认，编号跨批连续；所有批次完成才进闸门 | 功能阶段审查要等最后一个任务（第 101 分钟）才开始 |

其中 112–114 只改提示与技能（程序不强制），效果要靠复跑验证；110、111、115–117 由程序执行，都有端到端测试。

## 9. 待办与待决定

- **复跑验证第 108–117 条**：用全 gpt 再跑一次看板，重点看规划时长、任务数与运行次数、修订次数、阶段审查与合并的等待时间，与原生 pi 的 21.5 分钟对比。
- **需求变更流程**：复跑二停在 F1，architect 反复要求确认契约细节。下一步看实验脚本的代答方式（只说"同意建议"，没带上具体方案）是否需要改，或者 F1 是否应该在默认方案明确时直接采用。
- **用户全局设置**：`~/.pi/agent/pi-flow.json` 当前所有角色都是 `openai-codex/gpt-6.1-sol`（high）。复跑二之前的设置（实施角色用 glm，失败后升级到 gpt）备份在作业临时目录，作业删除后会清掉。
- **整体判断**：对四五千行以内、需求清楚的项目，pi-flow 很难追上单会话强模型。它的价值要在更大的项目上验证：一个会话装不下、需要多人长期并行、需求会多次变更的场景。
