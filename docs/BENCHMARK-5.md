# 第五轮实验方案：已有大仓库上的多需求并行

> 记于 2026-10-04。目的：验证 pi-flow 在原生 Pi 开始吃力的场景里是否更可靠。看板（约 4000 行）只保留为回归冒烟，不再作为优化目标。
> 每种做法只跑一次，所以判定标准有意定得粗：小差异一律算持平。**判定标准在开跑前定下，跑完不改。**

## 1. 仓库

**选定：[Homebox](https://github.com/sysadminsmedia/homebox) v0.26.2（提交 `e01dd73`）**，家庭物品与资产管理系统。

| 项 | 情况（本机已核实） |
|---|---|
| 规模 | 约 7.3 万行（Go、TS、Vue、SQL；不含 ent 生成代码、依赖、翻译文件） |
| 结构 | Go 后端（chi 路由、服务层、仓储层）＋ ent ORM 与 goose 迁移（sqlite3、postgres 两套）＋ Nuxt/Vue 前端（TS）。后端、数据库、前端三个角色能自然并行 |
| 运行 | 纯本地，SQLite，不需要 Docker 或外部服务 |
| 测试 | 后端 `go test ./...` 约 80 秒，全部通过，只有 `TestValidateNotifierURL` 的 2 个子用例依赖外网 DNS 解析，本机失败（两边都跳过）；前端 API 集成测试（vitest，对着运行中的服务）60/60 通过；`go vet`、前端 `lint` 通过 |
| 已有缺陷 | 前端 `nuxi typecheck` 在上游就有类型错误，不作为验证命令 |
| 代码生成 | `go generate ./internal/data/ent`（可在本机复现，无差异）；swagger 与前端类型生成需要 `swag`（已安装到 `~/go/bin`） |
| 知名度 | 中等（hay-kot/homebox 的社区分支），新功能是我们自己设计的，训练数据里不会有答案 |

**放弃的候选**：

| 仓库 | 原因 |
|---|---|
| Uptime Kuma | 约 7.9 万行，但后端测试要 11.5 分钟且依赖外网（本机有失败用例）；接口走 socket.io，隐藏测试难写；非常知名 |
| Vikunja | 约 36 万行，太大 |
| Actual Budget | 约 33 万行，太大 |
| Homebox 主干 | 前端集成测试在主干上有失败，改用最近的发布版 |

## 2. 需求

三个需求同时给出，放进一个功能流程，由 architect 拆成任务并行做。每个需求都要动数据库、后端、前端。需求文本在准备阶段写进 `~/pi-flow-runs/homebox-input/`，下面是要点。每条编号对应隐藏测试里的一组用例。

**R1 借出记录**
1. 新表记录借出：物品、借给谁（文本）、借出时间、应还日期（可选）、归还时间、备注。
2. `POST /api/v1/entities/{id}/loans` 借出，返回 201；物品已借出未还时返回 409；别的组的物品返回 404。
3. `POST /api/v1/entities/{id}/loans/return` 归还；没有未还的借出时返回 409。
4. `GET /api/v1/entities/{id}/loans` 返回借出历史，按借出时间倒序。
5. `GET /api/v1/loans?status=open|overdue|all` 返回全组的借出记录；overdue 表示已过应还日期且未还。
6. 物品详情（`GET /api/v1/entities/{id}`）带 `currentLoan`，没有借出时为 null。
7. 删除物品时一并删除它的借出记录。
8. 前端：物品页有"借出 / 归还"按钮和借出历史；新增借出列表页（未还、逾期）。
9. sqlite3 与 postgres 两套迁移都要有。

**R2 数量变动记录**
1. 物品数量通过任何途径变化（创建、PUT、PATCH、复制、CSV 导入）都追加一条记录：旧值、新值、时间、操作用户、来源。
2. `POST /api/v1/entities/{id}/quantity-adjust {delta, reason}`：调整后小于 0 返回 422。
3. `GET /api/v1/entities/{id}/quantity-history` 按时间倒序。
4. 数量没有变化的更新不产生记录。
5. 前端：物品页有加减数量的控件（填写理由）和变动历史表。

**R3 批量操作**
1. `POST /api/v1/entities/bulk {ids, action, locationId?, tagIds?}`，action 为 move、tag（追加标签）、archive。
2. 要么全部成功，要么全部不变：任何一个 id 不存在或不属于本组时返回 404，什么也不改。
3. 把位置移到它自己或它的子孙下面时返回 422。
4. 移动后，开启了"子物品跟随位置"（`sync_child_entity_locations`）的物品，其子物品的位置同步更新，和单个移动的行为一致。
5. 前端：物品列表可以多选，出现批量操作栏。

**R4 中途追加的需求**（在第 20 分钟给出）
1. 借出中的物品不能删除（409 `ENTITY_ON_LOAN`）。
2. 批量操作中只要有一个物品借出中，move 和 archive 整体返回 409 `ENTITY_ON_LOAN`，什么也不改；tag 不受影响。
3. 数量调整的理由必填，最长 200 字，否则返回 422。
4. 前端：借出中的物品，删除按钮不可用并提示原因。

R4 故意横跨 R1、R2、R3，用来检验后期上下文退化和忘记约束的问题。

## 3. 两组做法与公平性

| | 原生 Pi | pi-flow |
|---|---|---|
| 模型 | `openai-codex/gpt-6.1-sol`（high），单会话 | 各角色同一个模型（high）；额度用完时可以换用 glm 作为后备（见第 4 节） |
| 扩展 | 全局安装的 serena、codegraph、web-access，两边相同 | 相同 |
| 仓库说明 | 仓库根目录的 `AGENTS.md`（开发命令、代码生成步骤、测试方式），两边是同一份 | 同一份；另外有 `/flow init` 生成的规则与 workflow.yaml |
| 需求输入 | 同一份需求文本 | 同一份 |
| 上下文 | 允许 Pi 自己压缩上下文 | — |
| 被杀后恢复 | `pi --continue` 接着原会话，发"继续" | `/flow resume` |
| 自检 | 允许自己跑测试、启动服务 | 相同 |

两组按顺序跑，不同时跑，避免争用机器和额度。

## 4. 故障注入（两边时间点相同，从开始计时）

| 时间 | 事件 | 原生 Pi | pi-flow |
|---|---|---|---|
| 20 分钟 | 追加需求 R4 | 在会话里发出 R4 文本 | 用 `/flow replan` 转达 R4 |
| 35 分钟 | 杀掉进程 | `kill -9` pi 进程，10 秒后用 `pi --continue` 恢复 | `kill -9` 主进程与全部子进程，10 秒后 `/flow resume` |
| 50–65 分钟 | 主模型额度用完 15 分钟 | 本地代理对 gpt 请求返回额度错误；会话停下后，脚本按普通用户的做法每 5 分钟重试一次"继续" | 同一个代理；pi-flow 自己暂停这个模型，实施角色换用 glm 或等待恢复 |

- **额度限制的模拟**：Pi 文档说明 `models.json` 里只给已有 provider 写 `baseUrl` 会保留它的内置模型，所以可以把 openai-codex 指到本地代理，在窗口期内返回额度错误、其余时间原样转发。准备阶段先核实这条路能走通；走不通就退回"窗口期内杀进程、窗口结束后再恢复"，两边相同。
- **单独计分**：pi-flow 能换模型是它的设计优势，但测的是多模型调度，不是工作流本身是否可靠。额度窗口的影响（损失的时间、是否需要人工）单独记一栏，不并入完成率等主要指标。
- 某一边在事件发生前就已经完成时：R4 作为一次新的变更请求给出；杀进程和额度限制记为"未触发"。

## 5. 指标

| 指标 | 定义与统计方法 |
|---|---|
| 完成率 | 隐藏验收测试的通过率，按 R1–R4 分别统计、再算合计。某个需求通过 ≥ 90% 才算"完成" |
| 回归 bug 数 | 基线上通过、改完后失败的用例数，来源有三处：仓库自带的后端测试、前端集成测试、我写的现有功能隐藏回归测试（物品增删改查、位置树与路径、标签、维护记录、导入导出、统计） |
| 误改文件数 | 改动了允许范围之外的文件，允许范围按需求事先列出（第 6 节）；另外人工检查有没有删测试、放宽已有断言。删一个测试或放宽一个断言计 1 |
| 需求遗漏 | 第 2 节的编号要点中，对应隐藏测试全部失败的条数，即完全没做的要点 |
| 恢复能力 | 杀进程后：是否恢复成功；丢失或重复的工作（恢复前后 `git diff` 对比）；从恢复到重新开始产出（第一次写文件）的时间 |
| 人工干预次数 | 分两类：**必需确认**（pi-flow 闸门批准、原生 Pi 的启动与追加需求，都是脚本内置）与**纠正性干预**（回答问题、催促"继续"、处理卡住、清理残留）。只比较纠正性干预 |
| 总耗时 | 从开始到最后一次停止的墙钟时间（含额度窗口） |
| token 与花费 | 输入、输出、缓存读；花费按 run 记录的单价估算 |

**前端的验证**：先过 `nuxt generate` 构建和 lint；每个需求另配 1–2 条 Playwright 冒烟（用仓库已有的 Playwright 配置与本机 Chrome），例如借出后物品页显示"已借出"、勾选两个物品后出现批量操作栏。

## 7. 判定标准（开跑前定下，不改）

先看原生 Pi 有没有真的吃力。如果它满足下面四条，说明这个场景对单会话强模型仍然轻松，**pi-flow 的价值在这个规模上没有被证明**，结论按"持平"处理：
- 隐藏验收 ≥ 95%；
- 回归 0 个；
- 误改 0 个；
- 杀进程后恢复成功。

**主要指标**：完成率、回归 bug 数、误改文件数、需求遗漏、恢复能力。差异小于下面的阈值时算持平。

| 指标 | pi-flow 算"明显更好"的条件 |
|---|---|
| 完成率 | 隐藏验收合计高出 ≥ 10 个百分点，或多完成至少 1 个需求 |
| 回归 | 少至少 2 个，或原生 ≥ 2 个而 pi-flow 为 0 |
| 误改 | pi-flow 为 0，且原生 ≥ 2 |
| 需求遗漏 | 少至少 2 条 |
| 恢复 | pi-flow 恢复后不丢工作、不需要纠正性干预，而原生丢了工作或需要干预 |

**结论**：

| 结论 | 条件 | 之后怎么做 |
|---|---|---|
| **证明价值** | 至少 2 项"明显更好"；没有一项主要指标明显更差（完成率低 ≥ 10 个百分点、回归多 ≥ 2、误改多 ≥ 2 都算明显更差）；总耗时 ≤ 原生的 3 倍 | 保留工作流，下一步只优化成本：找出贡献最大的部分，削掉没有贡献的 |
| **持平** | 没有达到"证明价值"，也没有明显更差 | 砍掉大部分工作流：保留越界拦截（guard）、合并队列、崩溃恢复和多模型调度；去掉函数级契约、阶段审查、多角色拆分与设计阶段文档，让单个强模型在 worktree 里直接做，合并时跑全量测试 |
| **更差** | 任一项主要指标明显更差，且没有一项明显更好 | 同"持平"，砍得更彻底，并重新考虑项目方向 |

花费不参与判定（已知 pi-flow 贵），但会写进结论供参考。总耗时超过原生 3 倍时，即使质量更好也不算"证明价值"，只记为"质量更好但太慢"，再单独讨论。

## 8. 开跑前要做的准备

| 项 | 内容 |
|---|---|
| 基线仓库 | 固定 v0.26.2；提交一份 `AGENTS.md`（开发命令、代码生成、测试方式）；把前端测试端口改为读环境变量，避免多个 worktree 并行跑测试时抢 7745 端口；写一个 `bench/test.sh`（构建后端、在空闲端口起服务、跑 vitest、停服务）。两边从同一个提交开始 |
| 隐藏测试 | `~/pi-flow-runs/homebox-bench/`：R1–R4 验收（HTTP）、现有功能回归、前端 Playwright 冒烟。先在基线上跑一遍：回归部分全过，验收部分全失败 |
| 误改统计脚本 | 按第 6 节的允许范围统计 diff |
| pi-flow：已有仓库起步 | 之前只从空仓库新建过。需要核实 `/flow init` 在已有的 Go + Nuxt 仓库上能否生成可用的 workflow.yaml（命令、各角色的可写范围），以及功能流程能否直接在已有代码上开始。预计会先暴露一些问题 |
| 实验脚本 | `real-build.ts` 与 `baseline-build.ts` 加上时间线：第 20 分钟追加需求、第 35 分钟杀进程并恢复、额度代理的开关；记录每类人工干预 |
| 额度代理 | 核实 `models.json` 的 baseUrl 覆盖对 openai-codex 是否可行，写一个转发代理 |

**预计成本**：
- 原生 Pi 约 1 小时，几美元；
- pi-flow 约 3–5 小时、20–40 美元（按看板的比例粗估）；
- 准备工作（隐藏测试、脚本、已有仓库起步的修复）是主要的人工耗时。
