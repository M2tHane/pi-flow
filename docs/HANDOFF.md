### A. 验收测试必须先失败（构建与功能模式）

**问题**：修复模式的复现测试要求先失败（`src/core/verify-runner.ts` 的 `runReproVerify`，`src/core/dispatcher.ts` 中 `expectFail` 只对 fix 模式的 test 任务生效）。构建与功能模式的 kind=test 任务没有这项检查，"必然通过"的测试可以一路过审、过验证。

**难点**：修复模式里复现测试确认后直接 done，由修复任务把它一起带入主分支。构建模式里如果让验收测试先单独合入集成分支，集成分支会一直是红的，其他任务的合并后验证（全量 test）都会失败。

**推荐方案**（与修复模式一致）：
- test 任务审查通过后，程序运行 verify 并**要求失败**（复用 `runReproVerify` 的逻辑），确认后转 done，但**不进合并队列**。
- 硬依赖它的 impl 任务的 worktree 从 test 任务的分支末端建立（参考 `src/modes/fix.ts` 中修复任务的做法：预先建 worktree，`addTasks` 时传入 worktree、branch、base_sha），合并时把测试一并带入集成分支。
- 一个 test 任务被多个 impl 任务硬依赖时：选一个"承载者"（例如编号最小的那个），其余 impl 任务改为对承载者的硬依赖，或者在承载者合入后再从集成分支开工。需要在实现前确定规则，并在 `decompose-dag` 技能中说明"一个验收测试任务对应一个实现任务"的拆法。

**备选方案**：test 任务正常合入，但测试框架层面标记为待实现（skip），由 impl 任务去掉标记。这依赖测试框架，不推荐作为默认。

**验收**：
- 写了"必然通过"测试的 test 任务被打回，原因写明"验收测试没有失败"。
- 测试与实现一并进入集成分支。
- 集成分支在任何时刻都不因为未实现的验收测试而变红。

### B. 上游任务的经验传给下游（与 C 一起做）

**问题**：`dispatcher.ts` 的 `buildSpec` 只把任务自己的 handoff 放进提示（`handoff: store.readHandoff(flowId, task.id)`）。T-005 硬依赖 T-003，却看不到 T-003 的 handoff。

**做法**：派发时附上它所依赖任务（硬依赖与软依赖）的 handoff 摘要，放在动态部分，控制长度（每个上游最多若干百字，取最近部分）。

**验收**：下游任务的提示中出现上游任务 handoff 的摘要；长度受限；没有上游时不出现这一节。

### C. 项目级知识库（用户新增的需求）

**需求**：整个项目要有一个"项目级知识"不断积累的地方。它跨流程存在（build、feature、fix 都能用、都能贡献），让后来的任务不重复踩坑、遵守已形成的约定。

**设计约束**：
- 状态只能由程序写：agent 不能直接改知识库，只能通过工具提交条目，由程序校验后写入。
- 规则（`rules/`）只有用户能改：知识条目不能变相成为规则；要变成规则，必须走"规则草案 → 用户应用"的路径（`/flow rules apply`，见 `src/core/rules-draft.ts`）。
- 注入提示要考虑缓存：知识库变化会让子进程提示的前缀变化。

**建议设计**：
- **存储**：`.flow/knowledge.jsonl`（登记哈希，纳入完整性校验）或 `docs/KNOWLEDGE.md`（由程序生成）。条目字段建议包括：id、类别（约定、坑、决策、环境、外部依赖）、内容、适用范围（scope 或路径 glob）、来源（流程、任务、run、角色）、时间、状态（active、superseded、promoted）。
- **写入**：
  - 新增工具 `flow_learn`，给实施、审查、探查角色用。提交一条知识，程序校验后写入：去重，限长，范围合法。
  - reviewer 的打回与通过意见、合并后验证失败的原因，可以由程序自动提炼为候选条目，状态为 candidate，需要确认后才生效（是否需要人工确认，与用户讨论后决定）。
- **使用**：派发时按任务 scopes 与 writes 选出相关条目注入提示。建议放在规则之后、任务说明之前。条目按 id 排序且只追加，尽量保持前缀稳定。
- **管理**：新增 `/flow knowledge`：
  - 列出、搜索知识条目；
  - 废弃条目；
  - 把一条或几条提升为规则草案，再经 `/flow rules apply` 应用。
- **展示**：`/flow status --detail` 显示最近新增的条目；访谈者（`agents/interviewer.md`）在访谈新功能时可以读取。

**验收**：
- 一个任务提交的知识，能被后续同 scope 的任务在提示中看到。
- 跨流程依然存在。
- agent 无法直接改知识库文件。
- 有完整性校验覆盖。
- 可以废弃条目，可以提升为规则草案。

### D. 租约续期（心跳）

**问题**：租约固定 `limits.lease_minutes`（默认 45 分钟），长任务会被 `Engine.checkLeases` 强行杀掉。

**做法**：
- 子进程扩展（`src/pi-adapter/subagent.ts`）在每次工具调用时续租（例如距离过期不足一半时，把 `expires_at` 延长到"现在 + lease_minutes"）。
- 续租要经过 StateStore 的事务，并校验 token。注意写入频率：只在需要时续，避免每次工具调用都产生一次 git 提交。
- 长时间没有任何工具调用的，才真正判定过期。

**验收**：持续调用工具的任务超过 45 分钟不会被杀；卡住不动的仍会按时过期。

### E. 子进程会话留档

**问题**：子进程以 `--no-session` 运行（`src/pi-adapter/launcher.ts`），任务失败后无从复盘。

**做法**：
- 子进程会话保存到 `<项目>.worktrees/.sessions/<run>/`（不放 `.flow/`，避免成为未登记文件），用 Pi 的 `--session-dir` 或 `--session`。参数先查 `pi --help` 与 docs/sessions.md、session-format.md 核实。
- run 记录中保存会话文件路径。
- `/flow doctor --fix` 按保留期清理。
- 提供查看入口，例如 `/flow run <run_id>`：显示该 run 的工具调用摘要与最后的回复，或给出会话文件路径。
- 这也为以后"中断后接着原对话继续跑"打基础（NOTES 第 68 条，本轮不做续跑）。

**验收**：失败任务的每次 run 都能查到会话记录；过期记录可以清理。

### F. 集成分支定期同步主分支

**问题**：build/feature 流程持续期间，用户在 main 上的提交、fix 流程直接合入 main 的改动，都不会进入集成分支，冲突集中在最后合入时爆发（`src/core/release.ts` 的 `mergeToMain`）。

**做法**：在阶段边界（每个阶段 done、进入下一阶段时），程序把 main 合入集成分支。
- 必须串行：与合并队列互斥，可以作为合并队列中的一种特殊条目。
- 冲突处理复用现有规则：只涉及某个任务 writes 时生成 merge-fix，涉及契约或受保护路径时停下来交给用户。
- 注意 `.flow/` 的状态提交也在 main 上（见 J 项）：同步时要排除或无视 `.flow/` 的差异。
- 也可以提供 `/flow sync` 让用户手动触发。

**验收**：流程期间 main 上的改动在下一个阶段开始时进入集成分支；有冲突时按规则处理；最终合入主分支时不再出现这些冲突。

### G. 执行中修订计划

**问题**：执行阶段发现漏了任务或拆分有误，只能 `flow_block`，再靠用户手动处理。

**做法**：
- 执行阶段（S2–S4）允许提出"计划修订"：增加任务、调整未开始任务的依赖、取消未开始的任务。
- 可以由 architect 经新的派发提出（例如 `/flow replan "<原因>"` 派 architect 读取现状后调用 `flow_propose_tasks` 的修订形式），也可以由阻塞任务触发。
- 修订作为一次小型闸门，由用户批准（复用提案、DAG 报告与 `approveStage` 中重新编号落地的逻辑，见 `src/core/stages.ts`），批准后程序增删任务。
- 已开始或已完成的任务不能被修改或取消。取消需要新增转移（例如 `pending/ready → cancelled`），在状态机中登记为偏离。

**验收**：可以在 S3 中途增加任务并正常调度；未开始的任务可以取消；正在进行的任务不受影响；必须经用户批准。

### H. 按风险审查

**问题**：每个任务都由 reviewer（默认强模型）审查，审查不计入并发上限（`state-store.ts` 中 `running_count` 只计 in_progress），成本高。

**做法**：
- 按任务风险选择审查方式。低风险例如：只改测试或文档、改动文件少、diff 行数少、不涉及 shared 与契约。
  - 低风险：用便宜模型审查，或只做程序检查直接通过。
  - 高风险：强模型审查。
- 判定规则写进 `workflow.yaml`（新增可选配置并校验），默认值要保守。
- 审查 run 计入一个单独的并发上限，避免同时起太多审查。

**验收**：低风险任务按配置走便宜审查或只做程序检查；高风险任务照常；审查并发受限。

### I. 失败后升级模型、成本预算

**做法**：
- **升级模型**：同一任务第 N 次尝试（可配置，默认第 2 次失败后）自动换成更强一档的模型（例如 medium → strong）。可以在 `/flow-config` 或 `workflow.yaml` 中为每个角色配置升级用的模型。run 记录写明是升级后的模型。
- **预算**：
  - `workflow.yaml` 新增可选的流程预算（token，或按 Pi 返回的 cost 金额）；
  - 用到一定比例（例如 80%）时在"需要你处理"中提醒；
  - 超出时暂停派发新任务，等用户提高预算或继续。

  成本数据来自 `.flow/runs`（`src/core/cost.ts`）。

**验收**：第二次失败后的派发使用升级模型；超预算时停止派发并提示用户；`/flow status --cost` 显示预算使用情况。

### J. 状态存储的性能与主分支历史

**问题**：
- 每次事务都要完整读取 `events.jsonl`（`state-store.ts` 的 `assertHeadConsistent`）。
- 每次状态变化都会触发通知检测（`status-view.ts` 的 `snapshotOf` 会读全部任务与事件）。
- 一个任务大约产生 13 个 `flow-state:` 提交，全部落在 main 上，污染历史，推送时也会被带上去。

**做法**：
- **事件日志**：只读末尾一条（从文件尾部反向读取）来校验 head；完整校验只在 resume 与 doctor 中做。
- **状态读取**：在 StateStore 中加内存缓存（按文件 mtime 或版本号失效）；通知检测做节流。
- **状态提交移出 main 的历史**：可以用独立的引用（例如 `refs/pi-flow/state`），配合 `git commit-tree` 直接写对象；也可以换一种不进 main 历史的提交方式。这一项影响面大：
  - 完整性校验与恢复依赖"`.flow/` 纳入 git"；
  - worktree 中也有 `.flow/` 的旧拷贝；
  - `release.ts` 与 `merge-queue.ts` 中多处假设状态提交在当前分支上；
  - 需要先写方案，与用户确认后再改。

  原始需求第 2 节第 4 条要求"每次状态转移都 git commit"，改动后仍要满足（提交到专用引用上）。

**验收**：
- 事件数上千时，单次转移的耗时不随事件数线性增长（加一个性能测试）。
- main 的历史中不再出现 `flow-state:` 提交。
- 恢复与完整性校验照常工作。

### K. 合并列车（视规模决定）

**问题**：合并严格串行，每次都跑合并后验证，任务多时队列成为瓶颈。

**做法**：在当前任务合并验证的同时，基于"集成分支 + 当前任务"预先验证下一个任务；当前任务失败时，下一个回退重来。

**建议**：先测量（例如 20 个小任务的流程，合并队列总耗时占比），确认是瓶颈再做。不做也要在汇报中给出测量数据。

### L. 实时进度显示

**做法**：
- 在调度模式下，用 Pi 的 `ctx.ui.setStatus` 或 `setWidget` 在状态栏显示：当前阶段、进度、正在运行的任务。API 见 Pi docs/extensions.md 与 tui.md，先核实。
- 只在终端界面（`ctx.mode === 'tui'`）生效。
- 刷新挂在引擎的 `onChange` 上，并做节流。

**验收**：任务开始、结束时，状态栏随之变化；退出调度模式后状态栏清除。

## 3. 建议顺序

| 顺序 | 事项 | 理由 |
|---|---|---|
| 1 | A 验收测试先失败 | 堵住最大的质量漏洞 |
| 2 | B + C 上游经验与项目级知识库 | 同一处改动（提示组装与派发），一起设计 |
| 3 | D 租约续期、E 会话留档 | 小而独立，减少误杀、方便复盘 |
| 4 | F 集成分支同步 main | 避免最终合入冲突 |
| 5 | G 执行中修订计划 | 依赖提案与闸门逻辑，较复杂 |
| 6 | H 按风险审查、I 升级模型与预算 | 成本控制，涉及 workflow.yaml 新配置 |
| 7 | J 状态存储（先性能，后提交位置） | 提交位置改动大，需要先出方案并确认 |
| 8 | L 实时进度 | 体验改进 |
| 9 | K 合并列车 | 先测量再决定 |

## 4. 工作须知（踩过的坑）

- **Pi API**：一律先查 `$(npm root -g)/@earendil-works/pi-coding-agent/docs` 与 `dist/**/*.d.ts`。只有 `src/pi-adapter/` 可以调用 Pi API；新用到的 API 先在 `src/pi-adapter/pi-api.d.ts` 中补最小类型声明。
- **子进程必须关闭 stdin**（`stdio: ['ignore', ...]`），否则 `pi -p` 会一直等待输入。
- **guard 必须是子进程最后加载的扩展**：`tool_call` 处理函数按加载顺序执行，后面的处理函数能改参数且不再校验。
- **测试中启动 pi 必须用异步的 `spawn`**：假 LLM 服务在测试进程内，`spawnSync` 会阻塞事件循环导致死锁。
- **macOS 的 `/var` 是 `/private/var` 的符号链接**：比较 git 给出的路径前先 `realpath`。
- **代码只用可擦除的 TypeScript 语法**（Node 原生类型剥离）：不用参数属性、enum、namespace。
- **改 `src/core/schemas.ts` 后执行 `npm run gen:schemas`**。新增持久化文件要在 `state-store.ts` 的 `schemaKindOf` 中登记，以便完整性校验。
- **状态转移只能经过 `state-machine.ts` 的转移表**。新增转移要写测试，并在 NOTES 中登记为偏离。
- **测试分层**：
  - `test/fixtures/fake-subagent`（进程内脚本，快）；
  - `test/fixtures/fake-llm`（真实 pi 子进程加假模型，支持 `variants` 与 `delay_ms`）；
  - 真实模型冒烟：`node scripts/demo.ts --real-fix`。
- **成批替换文本时，确认只命中一处**：曾经因为同一段代码在两个测试中重复，替换出了错误。
- **修改 `agents/`、`rules/`、`skills/` 后**，在 NOTES 的"缓存提醒"中记一笔，并在汇报中提醒用户。
