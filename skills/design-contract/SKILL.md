# 设计契约

**契约是把讨论定下来的需求落成文档，不是扩展需求。** 后面的实现和审查都严格照着它来，契约里每多一条要求，
实现就多一处可能被打回的地方。

- 只写需求（PRD、需求摘要）里有的功能，把它们写成数据模型、接口、错误码与必要的行为细节。
- 不新增需求没有的能力（例如没要求回滚就不设计迁移回滚，没要求就不做通用的 JSON Schema 引擎、插件机制、多版本 API）。
  实现手段（用什么函数、怎么组织代码）留给实施者，不写进契约。
- 确实需要超出需求的设计（安全、数据完整性上不得不做的），在 flow_propose_tasks 的 extras 里逐条写明是什么、为什么，
  由用户批准时决定。不写进 extras 的超出部分，审查会当作缺陷。
- 需求本身不清楚的地方，在需求阶段就用 flow_block 问清楚，不要在契约里替用户定。

1. 先定数据模型：核心实体、字段、约束、关系。schema 只在一处定义（src/shared），类型与校验由它派生。
2. 再定模块边界与依赖方向，写入 docs/ARCHITECTURE.md。
3. 最后定接口：在 docs/contracts/ 中为每个模块写 API 契约（路径、方法、请求与响应 schema、错误码）。
4. 契约要能被测试直接引用：实现、实施者自己的测试与后面的联调测试都对着契约写，因此实现之间可以用软依赖并行。
5. 每个重大选型（框架、数据库、鉴权方式等）写一条 ADR：背景、选项对比、建议、影响。不替用户拍板，在 ADR 中写"建议"。
6. 契约在阶段批准后只读；运行中要改，走"修订计划"：由修订新增一个改契约的任务（见 revise-plan）。

## 规则与命令草案
技术栈定下来后，按技能 write-rules 在 `docs/rules-draft/` 写针对本项目的规则草案与命令草案（你不能改 `rules/` 与 workflow.yaml，由用户决定是否应用）。
