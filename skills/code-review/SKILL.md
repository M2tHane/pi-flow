# 代码审查

（改编自 mattpocock/skills 的 code-review，MIT 许可，Copyright (c) 2026 Matt Pocock。原技能有"规范"与"需求"两个维度；需求维度由 pi-flow 的独立验收负责，这里只保留规范维度。）

## 先找依据
- 项目的成文规范：rules/global.md、rules/project.md、AGENTS.md，以及仓库里写明编码约定的文档（CONTRIBUTING.md 等）。
- 工具已经在管的（格式化、lint 规则、类型检查）不提。

## 两类问题
- **违反成文规范**：引用规范的出处（文件 + 哪一条），可以是"必须改"。
- **坏味道**（下面的基线，出自 Fowler《重构》第 3 章）：永远是判断，只能是"建议"，写成"可能是……"。项目规范明确认可的写法，不按坏味道提。
- 明确的缺陷（必然出错的边界、资源泄漏、注入、吞掉的错误）也可以是"必须改"，依据写清楚会在什么输入下出什么错。

## 坏味道基线（是什么 → 怎么改）
- **名字说不清**：函数、变量、类型的名字看不出做什么或装什么 → 改名；想不出诚实的名字，说明设计含糊。
- **重复代码**：同样的逻辑在改动的多处出现 → 抽出共同部分，两处都调用它。
- **依恋情结**：一个函数用别的对象的数据比用自己的还多 → 把它挪到那份数据旁边。
- **数据泥团**：几个字段或参数总是一起出现 → 合成一个类型传递。
- **基本类型偏执**：用字符串或数字代表本该有自己类型的领域概念 → 给它一个小类型。
- **重复的分支**：同一类型上的 switch / if 链在多处出现 → 用一张共享的映射表或多态替代。
- **霰弹式修改**：一个逻辑改动要散落地改很多文件 → 把一起变化的东西放进一个模块。
- **发散式变化**：一个文件因为几件不相关的事被修改 → 拆开，让每个模块只因一件事变化。
- **夸夸其谈的通用性**：为需求里没有的场景加的抽象、参数、钩子 → 删掉，等真需要时再加。
- **过长的调用链**：a.b().c().d() 这种调用方不该依赖的导航 → 在第一个对象上用一个方法隐藏这段路径。
- **中间人**：一个类或函数几乎只是转手调用 → 去掉它，直接调用真正的目标。
- **被拒绝的遗赠**：子类或实现者忽略或覆盖了继承来的大部分东西 → 不用继承，改用组合。

## 写法
- 每条问题写清：依据（规范出处或坏味道名称）、文件、位置（函数名或行号范围）、问题、期望怎么改。
- 只审这次改动里的代码；改动之外的老问题不提。
- 宁缺毋滥：没有问题就报告没有问题；同一类问题合并成一条，列出所有位置。
