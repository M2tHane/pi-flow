# 拆解任务 DAG

## 粒度：跟实施角色的模型强弱走
任务说明里列出了各实施角色用的模型。**每个任务都有固定开销**：子进程要重新读任务、契约和相关代码，合并前要跑一次全量测试。
任务越多，这部分开销越大；真实冒烟中强模型做 14 个任务、35 次运行，合计耗时是单会话的十几倍。

- **强模型**（与你同档）：按模块或按层拆大任务，一个任务可以是一整个后端模块组，10 到 30 个文件都可以。
- **弱模型**（便宜档、本地模型）：任务要小，"一次会话能完成"，通常 1 到 8 个文件；大任务容易做不完或原地打转。
- **小项目**（预计代码四五千行以内、模块不超过 8 个左右）且实施角色是强模型：**不按功能切片拆**，每个角色一个任务——
  S2 一个 infra 任务（骨架、依赖、存储层、公共类型）；S3 一个后端任务（全部接口，自带测试）、一个前端任务（全部页面，
  对着 REST 契约开发，软依赖后端）；S4 一个联调任务。一共四五个任务。
- 大项目或弱模型：按垂直切片拆，一个切片 = 一个用户可感知的能力（例如"创建订单"）。
- 每个任务的 writes 落在其角色的 scope 内，尽量用目录 glob（src/server/orders/**）。

## 尽早并行
- 实施阶段的总耗时取决于关键路径，不取决于任务总数。拆完先看开头几层：只有一个任务在跑的时间越短越好。
- 基础设施与公共底座（项目骨架、依赖、构建与测试配置、公共类型、存储层的通用读写）合并为尽量少的任务：
  一个 infra 任务（S2），必要时再加一个基础实现任务。**不要为底座再拆"先行验收测试 → 实现"两层**：
  底座的验证放在它自己的测试和 verify 里。
- 切片之间默认对着契约开发（软依赖 + integration 任务），不要让切片排成一串。
  切片只在确实需要另一个切片的代码才能编译或运行时才写硬依赖。
- flow_propose_tasks 返回的报告会提醒"开头几层只能串行"或"关键路径占比过高"（关键路径超过任务数的一半）；
  出现时优先按上面两条调整后重新提交。

## 测试：实施者边写边测，合并前跑全量
- 每个实现任务（一个切片，或强模型下的一整个模块）自带测试：实施者实现功能，同时为它写测试并跑通。任务的 writes 要包含该模块的测试目录
  （例如 src/server/accounts/** 与 tests/server/accounts/**），验收标准写清要测哪些行为，verify 填 test。
- 不要单独拆"先写验收测试、再实现"的测试任务（程序默认会拒绝：testing.leading_tests 为 false）。
  先于实现写的测试跑不出对错，写错了没有办法自动发现，真实冒烟中这是返工的最大来源。
- 跨模块的联调与端到端测试放在最后的阶段（S4，或功能流程的回归阶段），由 test-engineer 对着**已经实现的功能**写，
  硬依赖被测的实现任务。
- 每个任务合并前程序会跑全量测试；单个任务只需测自己写的功能。不逐个审查任务：阶段结束时统一审查一次、按模块修复，
  所以任务的验收标准与 inputs 里的契约条目要写清楚，阶段审查就对照它们。
- 改动已有接口（例如响应加字段）会让别的角色已有的测试失败：实施者可以直接修改这些已有测试来适配（程序允许，审查时核对），
  不必为"先兼容旧测试"单独拆任务或调整顺序；验收标准里写明哪些已有测试要随之更新即可。

## 验收标准要能被测试合理验证
- 验收测试只验证行为（输入 → 期望输出、错误路径）。
- 约束类要求（不用第三方依赖、使用某种语言、代码放在某个目录）不要写成验收测试：
  由 infra 任务的配置（例如 package.json 没有 dependencies）、任务的 writes 范围和阶段审查保证。
  让测试去扫描源码证明"没有第三方依赖"之类的要求，会让测试越写越复杂、越改越多。

## 依赖类型
- 硬依赖（hard）：后继需要前驱的产物才能编译或运行。例如 impl 依赖迁移建表、联调测试依赖被测的实现。必须写 reason。
- 软依赖（soft）：后继可以对着契约或 mock 先做。例如前端页面对着 API 契约开发，不必等后端实现。
- 每组软依赖必须有一个 kind=integration 的任务，对软依赖两端都是硬依赖，负责真实联调测试。
- 软依赖任务自己的 verify 不得包含需要对方实现的测试。
- 契约已在本阶段确定，所以"对着契约开发"默认写成软依赖。关键路径过长说明硬依赖用多了。
- 契约只覆盖模块之间的接口。同一模块内部需要互相调用的部分（例如前端的页面壳与各个页面、组件之间的回调）不要拆成
  对着契约并行的任务：放进同一个任务，或用硬依赖让后一个任务直接读前一个任务的代码。
- 例：记账服务拆成"账户、收支记录、分类、月度统计、CSV 导出"。不好的拆法：基础验收测试 → 基础实现 → 再分三条功能，
  前两层只有一个任务在跑。好的拆法：S2 一个 infra 任务（骨架、存储层、公共类型）；S3 每个功能一个实现任务（自带测试），
  功能之间对着契约开发，统计、导出对记录是软依赖；S4 一个 integration 任务由 test-engineer 联调（弱模型时）。
  实施角色是强模型时更好的拆法：这是个小项目，S2 一个 infra 任务、S3 一个后端任务做完五个功能（自带测试）、
  S4 一个联调任务，共三个任务。

## 热点文件规避
- 模块按目录自动发现，不集中登记路由或导出。
- 依赖与锁文件只由 infra 任务修改（S2 阶段）。
- 迁移文件用时间戳命名。
- 两个任务的 writes 重叠会被程序判为互斥、不能并行；尽量让 writes 不重叠。

## 提交
调用 flow_propose_tasks。id 用 T-001 起的临时编号；stage 取 S2（基础设施）、S3（切片）、S4（集成与端到端）。
每个任务的 inputs 列出它实现或调用的契约文件与条目（例如 `docs/contracts/accounts.md#createAccount`、
`docs/contracts/records.md#GET /records`），实施者按这些条目实现，阶段审查也对照它们。
校验失败会返回具体错误，修正后重新提交即可。
