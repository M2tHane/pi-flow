# 拆解任务 DAG

## 粒度
- 按垂直切片拆：一个切片 = 一个用户可感知的能力（例如"创建订单"）。
- 单任务粒度为"一次会话能完成"：通常 1 到 8 个文件。任务太细会增加固定开销。
- 每个任务的 writes 落在其角色的 scope 内，尽量用目录 glob（src/server/orders/**）。

## 尽早并行
- 实施阶段的总耗时取决于关键路径，不取决于任务总数。拆完先看开头几层：只有一个任务在跑的时间越短越好。
- 基础设施与公共底座（项目骨架、依赖、构建与测试配置、公共类型、存储层的通用读写）合并为尽量少的任务：
  一个 infra 任务（S2），必要时再加一个基础实现任务。**不要为底座再拆"先行验收测试 → 实现"两层**：
  底座的验证放在 infra 任务的 verify（能构建、空测试能跑）和后续切片的验收测试里。
- 切片之间默认对着契约开发（软依赖 + integration 任务），不要让切片排成一串。
  切片只在确实需要另一个切片的代码才能编译或运行时才写硬依赖。
- flow_propose_tasks 返回的报告会提醒"开头几层只能串行"或"关键路径占比过高"（关键路径超过任务数的一半）；
  出现时优先按上面两条调整后重新提交。

## 先 test 后 impl
- 每个**功能切片**先有一个 kind=test 的任务（test-engineer，写 tests/acceptance/**，依据验收标准），
  再有 kind=impl 的任务硬依赖它。实施者不得修改验收测试。
- 一个验收测试任务对应一个实现任务。程序会运行验收测试并**要求它先失败**，然后不单独合入，
  而是由硬依赖它的实现任务（承载者）从测试分支开工、合并时一并带入，集成分支不会因未实现的测试变红。
- 多个任务硬依赖同一个验收测试时，程序选其中最靠前的一个（通常编号最小）作承载者，其余改为硬依赖承载者；
  一个实现任务不能承载多个验收测试（会被拒绝）。需要多个切片共用的测试，拆成各自的测试任务。
- 验收测试任务必须有 verify（例如 test）。没有下游实现任务的测试（例如 S4 的端到端、回归测试）照常验证通过后合入。

## 验收标准要能被测试合理验证
- 验收测试只验证行为（输入 → 期望输出、错误路径）。
- 约束类要求（不用第三方依赖、使用某种语言、代码放在某个目录）不要写成验收测试：
  由 infra 任务的配置（例如 package.json 没有 dependencies）、任务的 writes 范围和审查保证。
  让测试去扫描源码证明"没有第三方依赖"之类的要求，会让测试越写越复杂、审查无休止地打回。

## 依赖类型
- 硬依赖（hard）：后继需要前驱的产物才能编译或运行。例如 impl 依赖迁移建表、依赖验收测试文件。必须写 reason。
- 软依赖（soft）：后继可以对着契约或 mock 先做。例如前端页面对着 API 契约开发，不必等后端实现。
- 每组软依赖必须有一个 kind=integration 的任务，对软依赖两端都是硬依赖，负责真实联调测试。
- 软依赖任务自己的 verify 不得包含需要对方实现的测试。
- 契约已在本阶段确定，所以"对着契约开发"默认写成软依赖。关键路径过长说明硬依赖用多了。
- 例：记账服务拆成"账户、收支记录、分类、月度统计、CSV 导出"。不好的拆法：基础验收测试 → 基础实现 → 再分三条功能，
  前两层只有一个任务在跑。好的拆法：S2 一个 infra 任务（骨架、存储层、公共类型）；S3 每个功能一对"验收测试 → 实现"，
  功能之间对着契约开发，统计、导出对记录是软依赖，最后一个 integration 任务联调。

## 热点文件规避
- 模块按目录自动发现，不集中登记路由或导出。
- 依赖与锁文件只由 infra 任务修改（S2 阶段）。
- 迁移文件用时间戳命名。
- 两个任务的 writes 重叠会被程序判为互斥、不能并行；尽量让 writes 不重叠。

## 提交
调用 flow_propose_tasks。id 用 T-001 起的临时编号；stage 取 S2（基础设施）、S3（切片）、S4（集成与端到端）。
校验失败会返回具体错误，修正后重新提交即可。
