# 划分模块

一个模块交给一个模型，从前端到测试全部由它完成，做完后由独立的验收者对照验收标准确认。划分得好，模块能并行、互不打架；划分得不好，
模块之间要反复对齐，或者一个模块大到一个会话装不下。

（切分规则部分改编自 mattpocock/skills 的 to-tickets，MIT 许可，Copyright (c) 2026 Matt Pocock。）

## 怎么划
- **纵向切片**：每个模块贯穿数据、接口、界面、测试这几层，是一条窄但完整的路径，做完就能单独演示、单独验收。例如"账户与认证"、"知识库"、"对话"。
  不要按层（前端、后端、数据库）切给不同模型；"只有数据表"、"只有接口"的模块没法验收。
- **铺垫性重构先做**："先让改动变容易，再做容易的改动"。已有代码需要先整理（抽出公共部分、拆开过大的文件、补上缺的扩展点）才好加功能时，
  把整理单独作为第一个模块，其他模块依赖它。
- **大范围机械改动例外**：改名、改共享类型、改数据库列名这类一处修改牵动整个代码库的改动，没法纵向切，切了也合不进去（每片都会让测试失败）。
  把它单独作为一个模块（writes 覆盖受影响的范围），排在依赖它的模块前面，其他模块不要同时改那些文件。
- **底座先行**：新项目的骨架、公共组件、认证、数据库连接通常是第一个模块。
- **大小跟实现者的模型走**（见任务说明里"实现者的模型"）：强模型一个模块可以是一块完整的业务功能（含前后端与测试），靠本地提交与笔记跨越上下文压缩；
  不是强模型时，模块要小到一次会话能做完。太小（一个接口、一个按钮）就合并。
- **依赖要少**：只有真的需要对方的代码才加依赖，并写 reason；互不依赖的模块会并行开工。依赖只表示"必须等它验收通过"，不要为了排顺序而加。
- **已有项目加功能**：先读代码，按现有的模块边界放；改动集中在一个现有模块时，只规划一个模块。

## 每个模块写什么（flow_propose_modules）
- title：模块名与它交付的、用户能看到的行为（不是"实现 X 层"）。
- writes：具体目录（前端、后端、测试都包括），例如 `backend/app/kb/**`、`frontend/src/pages/kb/**`、`backend/tests/kb/**`。
  不同模块的 writes 不要重叠；重叠的模块不能同时开工。
- shared：几个模块都会改的公共文件（路由注册、菜单、迁移目录、i18n 文案）。登记后可以写，不算互斥；合并时程序会处理冲突。
- acceptance：从需求说明的 done-when 来，每条都能实际运行验证；独立验收者会逐条确认，写得含糊就无法验收。
- depends_on：必须先完成（验收通过）的模块与原因。
- inputs：要先读的文件（需求说明、术语表、原型页面、接口文档）。

## 测试接口（写在 docs/modules.md 每个模块下）
实现者按 tdd 技能只在约定的接口上写测试。为每个模块写明"测试放在哪里"：对外的 REST 接口、服务的公开函数、页面的用户操作等。
挑关键路径和复杂逻辑，不要求每个函数都测；内部函数、私有方法、数据库表不是测试接口。

## 模块之间的接口（docs/interfaces/<模块>.md）
只写别的模块要调用的部分：REST 路径、方法、请求与响应字段，或服务函数的名字、参数、返回值、错误。模块内部的实现不写。
用术语表（docs/glossary.md）里的名词命名。实现者发现缺了需要的调用，可以在对方的接口文档里追加。

## 提交前自查
- 每个模块做完都能单独验收吗？有没有"只有一层"的模块？
- 每条依赖都是真的要用对方的代码吗？能并行的是否都并行了？
- 铺垫性重构、大范围机械改动是否单独成模块并排在前面？
- 模块大小和实现者的模型相称吗？
