# 划分模块

一个模块交给一个模型，从前端到测试全部由它完成，做完后由独立的验收者对照验收标准确认。划分得好，模块能并行、互不打架；划分得不好，
模块之间要反复对齐，或者一个模块大到一个会话装不下。

## 怎么划
- **按业务功能纵向切**：例如"账户与认证"、"知识库"、"对话"。不要按层（前端、后端、数据库）切给不同模型。
- **底座先行**：项目骨架、公共组件、认证、数据库连接通常是第一个模块，其他模块依赖它。
- **大小适中**：一个模块是一块完整、可以独立验收的功能，通常 1 到 3 个页面加对应的接口。太大就按子功能再分；太小（一个接口、一个按钮）就合并。
- **依赖要少**：只有真的需要对方的代码才加依赖，并写 reason；互不依赖的模块会并行开工。
- **已有项目加功能**：先读代码，按现有的模块边界放；改动集中在一个现有模块时，只规划一个模块。

## 每个模块写什么（flow_propose_modules）
- title：模块名与负责的事。
- writes：具体目录（前端、后端、测试都包括），例如 `backend/app/kb/**`、`frontend/src/pages/kb/**`、`backend/tests/kb/**`。
  不同模块的 writes 不要重叠；重叠的模块不能同时开工。
- shared：几个模块都会改的公共文件（路由注册、菜单、迁移目录、i18n 文案）。登记后可以写，不算互斥；合并时程序会处理冲突。
- acceptance：从需求说明的 done-when 来，每条都能实际运行验证；独立验收者会逐条确认，写得含糊就无法验收。
- depends_on：必须先完成（验收通过）的模块与原因。
- inputs：要先读的文件（需求说明、原型页面、接口文档）。

## 模块之间的接口（docs/interfaces/<模块>.md）
只写别的模块要调用的部分：REST 路径、方法、请求与响应字段，或服务函数的名字、参数、返回值、错误。模块内部的实现不写。
实现者发现缺了需要的调用，可以在对方的接口文档里追加。
