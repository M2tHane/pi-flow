# 测试驱动开发

（改编自 mattpocock/skills 的 tdd，MIT 许可，Copyright (c) 2026 Matt Pocock。）

红 → 绿循环：先写一个会失败的测试，再写刚好让它通过的代码，然后下一个。下面每一节在每次循环里都适用。
测试名与接口用词和 docs/glossary.md 的术语一致。

## 什么是好测试
测试通过公开接口验证行为，不碰实现细节。实现可以整个重写，测试不用改。好的测试读起来像需求："有效的购物车能结账"直接说明有什么能力，
重构时也不会坏，因为它不关心内部结构。

## 测试放在哪里
只在约定的接口上写测试：docs/modules.md 里本模块的"测试接口"（对外 REST 接口、服务的公开函数、页面的用户操作）。
不可能什么都测，约定接口是为了把力气花在关键路径和复杂逻辑上，而不是每个边界情况。没写测试接口时，测对外接口与验收标准涉及的行为。

只在系统边界上 mock：外部 API（支付、邮件）、时间与随机数，必要时文件系统；数据库优先用测试库。不要 mock 自己写的模块和内部协作者。
需要 mock 的外部依赖用参数传进来，不在函数里直接创建。

## 三种坏测试
- **绑定实现**：mock 内部协作者、测私有方法、绕过接口去验证（直接查数据库而不是通过接口读）。特征：行为没变，一重构测试就坏。
- **同义反复**：断言用和代码相同的算法算期望值（`expect(add(a, b)).toBe(a + b)`、照着代码手推的快照、常量等于自己），永远不会和代码不一致。
  期望值要来自独立的依据：已知正确的字面量、算好的例子、需求说明。
- **横向切片**：先把测试全写完，再写实现。成批写出的测试验证的是想象中的行为，只测了形状，对真实的改动不敏感。改为纵向：一个测试 → 一段实现 → 重复，
  每个测试根据上一轮学到的东西来写。

## 循环的规则
- **先红后绿**：先写失败的测试，再写刚好通过的代码；不预先实现以后的测试要的东西，不加推测出来的功能。
- **一次一个切片**：一个接口、一个测试、一段最小实现。
- **重构不在循环里**：测试都绿了、本地提交之后再整理代码，整理完测试照样通过。
- 一个切片绿了就 `git commit`，并在笔记里把对应条目移到 done。
