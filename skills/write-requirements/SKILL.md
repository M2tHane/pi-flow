# 写需求说明

需求说明是后面所有工作的依据：原型照它画，模块照它划，验收照它逐条确认。写清楚比写得长重要。

## 结构
1. **背景与目标**：一两段，说清为谁解决什么问题。
2. **需求清单**：表格或编号列表，每条包含
   - 编号（R1、R2…）与一句话描述；
   - 优先级：MVP（这次必须做）/ 以后 / 不做；
   - done-when：怎样算做到，写成能测试或实际操作验证的形式（"POST /api/x 返回 201 和新记录"、"在列表页点删除并确认后，该行消失"）。
3. **关键决策与取舍**：采用了哪一方的意见、为什么。
4. **分歧与待你决定的问题**：每个问题给出选项与建议，用户批准前要拍板。
5. **界面风格**：打算用的风格与理由（配色、密度、气质，参考项目领域与使用者）；没有界面写"无界面"。
6. **范围外**：明确不做的事。

## 写法
- 用户视角与开发视角都要采纳：用户要的功能、开发提的成本与风险都体现在优先级和决策里。
- 需求没说清但有合理默认做法的，直接写默认做法，标注"默认"；只有真的需要用户决定的才列进待决定。
- 已有项目加功能：写清和现有功能的关系（复用、修改、不受影响），回归风险列在决策里。
- 不写实现细节（表结构、类名），那是规划阶段的事；接口路径与字段只在用户关心时写。
