# 写需求说明

需求说明是后面所有工作的依据：原型照它画，模块照它划，验收照它逐条确认。写清楚比写得长重要。只写和用户讨论定下的内容，不加用户没同意的功能。

## 结构
1. **背景与目标**：一两段，说清为谁解决什么问题。
2. **需求清单**：编号列表，每条包含
   - 编号（R1、R2…）与一句话描述；
   - 优先级：MVP（这次必须做）/ 以后 / 不做；
   - done-when：怎样算做到，写成能测试或实际操作验证的形式（"POST /api/x 返回 201 和新记录"、"在列表页点删除并确认后，该行消失"）。
3. **术语**：项目里的关键概念各用一句话定义，同一个东西只用一个叫法（"订单"就不再叫"单子"），后面的原型、规划、代码都沿用。
4. **关键决策与取舍**：讨论中定下的决定和理由；按默认处理的地方标"默认"。
5. **界面风格**：定下的风格与理由（配色、密度、气质，参考项目领域与使用者）；没有界面写"无界面"。
6. **范围外**：明确不做的事。

## 写法
- 已有项目加功能：写清和现有功能的关系（复用、修改、不受影响），回归风险写在决策里；术语沿用项目已有的叫法（见 docs/glossary.md）。
- 不写实现细节（表结构、类名），那是规划阶段的事；接口路径与字段只在用户关心时写。
- 提交时 prototype 参数说明是否需要原型阶段：有界面且用户想先看原型为 true；没有界面或只改后端为 false。
