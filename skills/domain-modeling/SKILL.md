# 领域建模：术语表与 ADR

（改编自 mattpocock/skills 的 domain-modeling，MIT 许可，Copyright (c) 2026 Matt Pocock。）

多个模型并行实现不同模块时，同一个概念很容易被叫成好几个名字（board / kanban / panel）。术语表让所有实现者、验收者用同一套名词，
代码、接口文档、测试的命名也就一致；概念精确了，模型也少花篇幅解释。

## 术语表（docs/glossary.md）
从需求说明的"术语"一节开始，结合需求与原型补全。已有项目加功能时先读现有的 glossary 与代码，沿用已有叫法，只补新概念。

格式：
```md
# <项目名>

<一两句：这个项目是什么。>

## 术语

**看板（Board）**：
一组按列排列的卡片，属于一个团队。
_不要叫_：面板、kanban

**卡片（Card）**：
看板上的一个待办事项，同一时间只在一列中。
_不要叫_：任务、条目
```

规则：
- **要有主见**：同一概念有几种叫法时选一个最好的，其余列在"不要叫"。中文名后附代码里用的英文名。
- **定义要短**：一两句，说它是什么，不说它做什么。
- **只收项目特有的概念**：超时、错误类型、工具函数这类通用编程概念不收。
- 概念自然成组时用小标题分组。
- 术语表里不写实现细节（表结构、类名、文件路径），它不是规格说明。
- 发现需求里的用词含糊或互相矛盾（同一个词指两件事），在术语表里定下精确的叫法，并写进 assumptions 请用户确认。

## ADR（docs/adr/NNNN-<slug>.md）
只在三条同时满足时才写：
1. **难以撤销**：以后改主意代价很大；
2. **没有上下文会让人意外**：以后的人看代码会问"为什么这么做"；
3. **确实有取舍**：有真正的备选方案，因为具体原因选了这个。

缺一条就不写。值得写的例子：架构形态（单仓、事件溯源）、模块之间的集成方式、有锁定成本的技术选择（数据库、认证、部署目标）、
边界与范围的决定（"用户数据归用户模块，其他模块只存 id"）、故意偏离常规的做法（"不用 ORM，因为……"）、代码里看不出的约束。

格式很短：标题加一到三句（背景、决定、原因）。只有备选方案值得记住时才加"考虑过的方案"，有不明显的后果时才加"后果"。
编号取 docs/adr/ 里最大的编号加一。
